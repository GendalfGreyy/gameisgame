# 01. Полное техническое задание (PRD / SRS)

## 1. Назначение

**TG Creator Studio** — мультирежимная no-code/low-code платформа конструирования игр и приложений в Telegram. На одном аккаунте доступны редактор для ПК и редактор для мобильного клиента Telegram. Данные проектов, движок выполнения и система публикации общие. Пользователь способен создавать проекты без программирования через компоненты, свойства, граф событий и визуальный интерфейс.

**Ценность:** создать, протестировать, опубликовать и отправить другу интерактивный проект, не устанавливая отдельный игровой редактор. Автору доступны черновики, версии и аналитика. Игроку — запуск проекта через ссылку Telegram.

**Не входит в обещание:** запуск нативного Unreal Engine 5, Nanite/Lumen, экспорт проекта в UE5, автоматическое создание персонального Telegram-бота у каждого автора, бесконечный открытый доступ к ОС пользователя, выполнение пользовательских JS-скриптов на сервере.

## 2. Цели и этапы продукта

- **R0 / доказательство архитектуры:** работающий сквозной 3D-проект от авторизации до запуска из Telegram.
- **R1 / функциональный конструктор:** полноценно применимый набор 3D, 2D и App Builder, Blueprint, assets, сохранения, публикации, адаптивные редакторы.
- **R2 / creator economy:** шаблоны, marketplace, расширенные графики и материалы, команды, кооперативное редактирование, мультиплеер, AI.

R0 не называется «полноценным Roblox Studio»; R1 — уже многофункциональная рабочая платформа, R2 — долгосрочная экосистема.

## 3. Участники и роли

| Роль                    | Возможности                                                                                           |
| ----------------------- | ----------------------------------------------------------------------------------------------------- |
| Гость                   | Публичный каталог и запуск доступных опубликованных проектов, если это разрешено продуктом            |
| Автор                   | Создавать проекты, изменять черновики, импортировать assets, играть, публиковать и снимать публикации |
| Участник команды (R2)   | Доступ по выданным правам Viewer, Editor, Publisher, Owner                                            |
| Игрок                   | Запуск опубликованной версии, сохранение игрового прогресса в разрешенных границах                    |
| Администратор платформы | Модерация, блокировка опасных материалов, управление лимитами, аудит действий                         |

Аккаунт привязывается к **проверенному сервером Telegram ID**. ID из небезопасных клиентских данных не дает доступа. На R0 авторизация через Telegram; для разработки — локальная имитация только в dev.

## 4. Основные пользовательские сценарии

**US-01:** из Telegram открыть Studio, нажать «Новый проект», выбрать 3D/2D/App, указать имя, получить проект с шаблоном.

**US-02:** на ПК добавлять объект drag & drop, менять положение/вращение/масштаб gizmo и числовыми полями, редактировать компоненты через Inspector.

**US-03:** на телефоне делать те же изменения через полноэкранную сцену, касания и нижние панели; объект можно переместить по оси с точным числовым вводом.

**US-04:** задать действие «кнопка → добавить очки» или «столкновение → уничтожить объект» визуальными узлами без написания кода.

**US-05:** выйти из редактора, зайти на другом устройстве и продолжить проект; получить статус сохранения и обработку конфликта версий.

**US-06:** запустить Play, проверить поведение, вернуться в Edit без порчи черновика, опубликовать снапшот, открыть ссылку в Telegram на втором аккаунте.

**US-07:** создать приложение с двумя страницами, формой, коллекцией данных, разрешениями, рабочим CRUD и опубликовать.

**US-08:** создать 2D-платформер с управлением и столкновениями, запустить на мобильном устройстве.

### 5.1. Редактор 3D (3D Studio)

Объекты: Empty, Cube, Sphere, Plane, Cylinder, Capsule, Light, Camera, Prefab, Imported glTF/GLB. У каждого объекта стабильный ID и компоненты Transform, Mesh/Model, Material, Camera, Light, RigidBody, Collider, ScriptGraph, Audio, Animation, PlayerController, Trigger. Render backend — PlayCanvas. Scene graph хранится в **нашей** схеме, не в сериализованной форме конкретного движка. Компонентный adapter превращает JSON-описание в объекты PlayCanvas.

Обязательно: 3D viewport с сеткой/осями/снаппингом, orbit/pan/zoom, выбор объекта касанием/мышью, raycasting, gizmos Move/Rotate/Scale, редактирование Inspector, моделирование на базе примитивов, импорт GLB, материалы (цвет/metalness/roughness/texture), камера и источники света. В Play Mode: управляемый персонаж, столкновения, триггеры, события. Версии на R2: terrain brush, shaders/node materials, particles, navigation mesh, advanced animation state machine, prefab variants, level streaming.

**Не включать в R0 собственный Blender/3D mesh sculptor**, сложные skeletal rigs или произвольные пользовательские шейдеры: они взрывают объем работ и усложняют безопасность.

### 5.2. Редактор 2D (2D Studio)

Canvas/viewport на PixiJS, сцена со Sprite, AnimatedSprite, Tilemap, Text, Parallax, Camera, Collider2D, RigidBody2D, Audio, ParticleEmitter (последний — R2). Загрузка PNG/WebP/sprite sheet; сетка, pivot, layer ordering, трансформации, анимации. Игровая физика отдельным модулем на Rapier 2D (Pixi — рендер, **не** готовая система коллизий и геймплея). На мобильном: виртуальный джойстик и buttons, назначаемые через визуальные события. Сценарий приемки: персонаж бежит и прыгает по платформам, подбирает монету, счетчик увеличивается.

### 5.3. Конструктор приложений (App Studio)

Дерево страниц/компонентов, React-based renderer **из allowlist компонентов**. Компоненты: Container, Stack, Grid, Text, Image, Button, Input, Textarea, Select, Checkbox, Form, Card, List, Tabs, Modal, Navigation, DataTable, Chart, Toast. Для всех: типизированные props, bindings, стили, доступность. Дизайн страницы задается JSON-схемой, а не произвольным JSX от автора. Поддержка layout breakpoints, темы Telegram и собственных дизайн-токенов.

Реальные действия без кода: Navigate, SetState, ShowModal, SubmitForm, CallApprovedAction, Data.Create, Data.Query, Data.Update, Data.Delete, ShowToast. Data Collections хранятся на сервере с пользовательскими/проектными правами, лимитами и фильтрами; права проверяются backend **для каждого запроса**, а не в UI. Подключение сторонних API — через серверный, изолированный capability proxy с allowlist, лимитами, защитой от SSRF и секретами только на backend.

### 5.4. Blueprint / Event Graph

React Flow используется **только для UI графа**. Наш `logic-engine` отвечает за валидацию, компиляцию в безопасное промежуточное представление и исполнение.

Набор узлов R1: Events (OnStart, OnClick, OnKey, OnCollision, OnTrigger, OnTimer, OnUpdate), Flow (Branch, Sequence, Delay, Once, Repeat с пределом итераций), Variables (Get/Set/Compare), Math/Boolean, Object (Spawn/Destroy/SetTransform), Physics (AddForce/Jump), UI (Show/Hide/SetText/Navigate), Data (approved CRUD), Audio (Play/Stop), Debug (Log). Порты типизированы (`exec`, `number`, `boolean`, `string`, `vec2`, `vec3`, `entityId`, `recordId`). Несовместимые порты не соединяются. Граф хранится JSON и проверяется перед публикацией.

Требования: ограничение числа выполняемых узлов/кадрового бюджета, обнаружение циклов без Delay, событийная очередь, отмена таймеров при остановке, понятная ошибка с ID узла, одинаковые функции в Edit Preview/Published Runtime. На сервере запрещен `eval`, произвольный пользовательский JS и код из Blueprint; backend выполняет только свои разрешенные действия.

### 5.5. Менеджер ресурсов

Форматы R1: 3D `.glb`, `.gltf` с валидируемыми зависимостями; изображения `.png`, `.webp`, `.jpg`; звук `.mp3`, `.ogg` (проверить совместимость браузера); шрифты разрешенных форматов. Рекомендовано нормализовать GLB с ресурсами, ограничивать геометрию/текстуры, принимать загрузки подписанными URL, проверять MIME/magic bytes, антивирусно сканировать по необходимости, создавать previews и thumbnails. Система hash/content-addressing экономит место, но владелец и права каждого asset обязательны. Нельзя исполнять произвольный HTML/SVG как доверенный контент.

### 5.6. Публикация

Черновик `draftRevision` редактируемый. При Publish сервер валидирует версию, ресурсы, узлы, лимиты и разрешения; фиксирует **immutable ProjectVersion**. Опубликованный Player по ID получает только version manifest и соответствующие assets. Удаление/редактирование черновика не должно подменять опубликованную версию. При Republish появляется новая версия; ссылка может вести на «актуальную опубликованную версию», при этом историческая версия остается идентифицируема по revision ID. `Unpublish` блокирует общий доступ, но не удаляет черновик.

На R1 ссылка вида `https://t.me/<studio_bot>?startapp=p_<publicId>`; `startapp` — только безопасный идентификатор маршрута, **не полномочие на доступ**. Для приватных проектов нужна независимая серверная проверка. Создать отдельного бота каждому автору автоматически **не входит** в R1.

### 5.7. Каталог и шаблоны

Встроенные шаблоны R1: 3D Obby/Platformer, 3D Room, 2D Platformer, 2D Clicker, App Catalog, App Form. Шаблоны — валидные ProjectSnapshot, применяемые в отдельный новый проект; их версии фиксируются. Публичный каталог модерируется. Комментарии, рейтинг, monetization и marketplace — R2.

## 6. Нефункциональные требования

- **Адаптивность:** рабочие ПК, планшет, телефон; ориентироваться также на `pointer: coarse`, safe area, доступную высоту, а не только ширину.
- **Performance budgets (цели для тестовых сцен, не гарантии):** мобильный Play 30 FPS на заданной эталонной сцене из 50 простых объектов; desktop Play 60 FPS на сцене из 100 примитивов. Проверять на заранее перечисленных устройствах и настройках графики. При падении — auto-quality/texture cap.
- **Устойчивость:** нет потери данных после штатного закрытия с подтвержденным сохранением; нестабильная сеть — IndexedDB черновой буфер и синхронизация.
- **Наблюдаемость:** trace-id на запрос, error tracker, client errors, FPS, latency, save revision, publish logs; не логировать токены и initData.
- **Доступ:** роль проверяется по каждому проекту и коллекции, rate limiting, quotas, безопасная загрузка файлов.
- **Развертывание:** HTTPS, отдельно dev/staging/prod, миграции базы, резервные копии PostgreSQL и S3, откат версий.
- **Поддержка:** Текущие стабильные версии библиотек фиксируются lockfile; API Telegram проверяется на клиенте по доступным возможностям/версии.

## 7. Монетизация (R2)

Планы по квотам проектов/хранилища/публикаций, creator marketplace, команды, ассеты, AI credits. Для цифровых товаров и услуг внутри Telegram необходимо отдельно соблюдать действующие требования Telegram к оплате, в том числе правила Telegram Stars. Не включать платежи до проверки актуальных правил.

## 8. Границы готовности

Работающая платформа — не перечень экранов и не `console.log` вместо действий. Проверка: реальный серверный CRUD, настоящая сцена, реальная физика/логика, жесты, возобновляемое сохранение и **независимый Player**, открываемый у другого пользователя.
